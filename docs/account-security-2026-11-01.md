# Восстановление пароля и подтверждение почты

1 ноября 2026 года. Код и локальная интеграция реализованы. Аккаунт Resend создан владельцем, почтовый домен подтверждён, отправка через HTTPS API включена в Railway. Проверка из production на официальный тестовый адрес Resend прошла. Полный путь с настоящим ящиком Proton проверен: регистрация, подтверждение почты, получение ссылки восстановления, самостоятельная смена пароля владельцем, повторный вход и получение уведомления о смене. Первый раскрытый ключ отозван по явному согласию владельца, действует только новый ключ замены.

## Путь клиента

- На входе есть «Забыли пароль?»: `/forgot-password`. Клиент вводит адрес, получает одинаковый ответ для существующего и неизвестного аккаунта. Настоящие инструкции отправляются только зарегистрированному адресу.
- Ссылка открывает `/reset-password`, новый пароль вводится дважды, от 8 до 128 символов. После применения нужно войти заново. Сайты, версии, публикация, формы и владелец аккаунта не меняются.
- В аккаунте `/account` видны статус почты и повторное письмо. После регистрации письмо отправляется автоматически, если почтовая доставка настроена. При отсутствии настройки регистрация остаётся доступной и честно объясняет недоступность подтверждения.
- Клик по ссылке `/verify-email` только открывает страницу. Подтверждение выполняется явной кнопкой и требует входа в тот аккаунт, который запросил письмо. Это не позволяет случайно активировать аккаунт, зарегистрированный кем-то на чужой адрес. На другом устройстве сначала нужно войти; форму можно оставить открытой, вход открыть в отдельной вкладке.
- Восстановление пароля само доказывает доступ к ящику и помечает адрес подтверждённым. Google-адрес подтверждается только на основании проверенных сервером `email_verified` claims; настройка Google по прежней просьбе владельца не возобновлялась.
- В боковом меню есть явная ссылка «Аккаунт» и статус неподтверждённой почты. Первая пробная генерация/публикация по-прежнему не требует регистрации. Новый обязательный запрет управления или публикации до подтверждения адреса не вводился.

## Безопасность

Ссылки содержат 256-битный случайный секрет. На диске токен хранится только как хеш имени файла, с назначением, аккаунтом, версией сессий и временем истечения. Восстановление действует 30 минут, подтверждение 24 часа. Токены одноразовые, получение страницы или проверка ссылки почтовым сканером не потребляют их. Параллельные попытки забрать один токен атомарно разделены, разные одновременные ссылки восстановления не могут обе сменить пароль.

Секрет помещён во fragment `#token=...`, не в query. Он не попадает в HTTP URL сервера и убирается из адресной строки после загрузки. Для этих страниц выставлены `no-store`, `no-referrer`, `noindex` и запрет встраивания во фрейм. Ссылки строятся из серверного `WINDX_AUTH_ORIGIN`, не из входящего Host/Forwarded. Из cookie или формы нельзя выбрать другого получателя письма подтверждения.

Смена пароля отзывает все прежние сессии и неиспользованные ссылки аккаунта через постоянный счётчик версий. Даже старые файлы сессий до внедрения этой функции перестают действовать после сброса. Данные пароля по-прежнему хешируются scrypt со случайной солью. Учётные записи остаются в том же файловом хранилище; миграция данных не нужна. Предварительно аутентифицированный старым паролем результат не может открыть новую сессию после сброса. Гостевая cookie не удаляется при восстановлении, чтобы при следующем входе сохранить возможность переноса пробника.

Лимиты запросов писем постоянные и переживают перезапуск: 60 запросов в час на сервис, 10 на источник, 3 на адрес и не чаще одного запроса на адрес в минуту. Это временные технические ограничения, не тариф. Завершение ссылок имеет отдельный лимит попыток в памяти процесса. Ограничители не являются полноценной внешней защитой от распределённой атаки.

Публичное восстановление обрабатывает отправку после ответа через Next `after`, чтобы длительность почтового API не раскрывала наличие аккаунта. Регистрация также не задерживается доставкой. Авторизованная повторная отправка подтверждения ждёт принятия письма API и показывает отказ поставщика. Получение API message ID не означает фактическую доставку во входящие. При ошибке отправки токен отзывается; в журнал пишется только общее сообщение без email, тела письма и секретов. После смены пароля дополнительно отправляется уведомление, если доставка включена. Нет самостоятельного постоянного почтового воркера и гарантированной очереди повторов после аварии: клиент может повторить запрос после паузы.

Сериализация изменения аккаунта рассчитана на текущую одну реплику файлового хранилища. Перед масштабированием на несколько реплик операции токенов/счётчиков/паролей нужно перенести в транзакционное хранилище.

## Доставка: бесплатный вариант подключён

Пользователь указал, что почтового сервиса пока нет и нужен бесплатный вариант. Подготовлен адаптер Resend HTTPS API, без нового SDK и без новых платных сервисов. На текущем Railway Hobby SMTP недоступен; повышать тариф ради SMTP не нужно. У Resend на дату проверки есть Free с 100 письмами в день. ### Конкретная причина ошибки пароля

При живой проверке владелец указал, что общее сообщение о совпадении и длине не объясняет отказ. Теперь клиент и сервер различают короткий пароль (`passwordShort`), слишком длинный (`passwordLong`) и несовпадение (`mismatch`). Короткий пароль показывает фактическое число символов и текущий минимум 8; несовпадение просит ввести одинаковое значение. Ошибка расположена непосредственно у соответствующего поля, связана с ним через `aria-describedby` / `aria-invalid`; после отправки фокус переходит в это поле. Введённые значения сохраняются. Формулировки есть на EN/RU/ES.

Сборка `npx next build --webpack`, eslint, `tests/account-security.mts` и полный `tests/account-security-http.mts` прошли.
