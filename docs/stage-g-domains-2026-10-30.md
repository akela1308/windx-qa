# Этап G: подключение своего домена

Дата: 30 октября 2026 года.

Реализован сценарий подключения одного точного доменного имени к сайту. Автоматические операции на рабочем хостинге включены после явного согласия владельца: создан отдельный project token WINDX production, сохранённый только в серверной переменной cabinet. Секрет не добавлялся в git, чат или клиентские props. Временный закрытый файл переноса удалён. Для стендов без ключа интерфейс по-прежнему честно сообщает, что подключение на платформе ещё не включено; там можно получить только TXT подтверждения владения. Настоящий внешний домен для сквозной проверки владелец не выбирал. Реальная цепочка DNS, Railway и HTTPS пока не проверена.

## Что получает клиент

В редакторе есть вкладка «Домен», также доступная из меню публикации. Интерфейс переведён на английский, русский и испанский. Управление доменами доступно владельцу с аккаунтом; создание пробного сайта и его первая публикация по-прежнему не требуют регистрации.

1. Владелец вводит уже принадлежащий ему домен или поддомен, без протокола и пути.
2. WINDX выдаёт индивидуальную TXT-запись `_windx.<адрес>`. Без её наличия в DNS приложение не добавляет домен в Railway и не занимает место на хостинге.
3. После подтверждения владения Railway возвращает настоящие записи адреса и своего подтверждения. WINDX показывает тип, полное имя и значение с кнопками копирования. Выдуманных значений CNAME, TXT или постоянного IP нет.
4. Кнопка проверки последовательно проверяет DNS, сертификат, состояние хостинга и ответ WINDX через HTTPS. Только после этого появляется статус «Подключён».
5. Отключение сначала прекращает выдачу сайта, затем удаляет точное подключение в Railway. Если хостинг не ответил, статус сообщает об ожидающей очистке и позволяет повторить отключение.

Перед удалением сайта нужно отключить домен. Сервер блокирует удаление связанного сайта, а карточка объясняет причину и открывает редактор. Это не оставляет занятый адрес без доступного владельцу управления.

Адрес `<slug>.windx.app` сохраняется. Подключение не публикует сайт и не изменяет документ, версии, заявки, поисковые метаданные или незавершённые правки. Take offline закрывает оба адреса; повторная публикация показывает новую опубликованную версию. Черновик через клиентский домен не доступен.

`example.co.uk` и `www.example.co.uk` являются отдельными подключениями. На этом этапе подключается один точный адрес, без автоматических редиректов между ними. Для корневого домена провайдер DNS должен поддерживать CNAME flattening, ALIAS или ANAME. Рекомендуемый первый адрес при отсутствии такой поддержки, `www`. Пользователь сам меняет записи в кабинете своего DNS-провайдера. WINDX не меняет серверы имён, почтовые записи и настройки других сайтов. На первом подключении нужен режим DNS без прокси; проверка сертификатов не отключается.

## Ограничение текущего хостинга

В правильном Railway workspace проверены Hobby и существующее подключение `*.windx.app`. Текущий лимит составляет два custom domains на сервис, то есть остаётся одно место для клиентского адреса. Приложение считает все существующие подключения и останавливается при достижении лимита. План, платные услуги и списания не меняются автоматически.

Это рабочая первая интеграция, а не готовая ёмкость для большого числа клиентов. До массового запуска нужно отдельно выбрать и согласовать инфраструктуру с достаточным числом клиентских доменов. Увеличение `WINDX_RAILWAY_DOMAIN_LIMIT` не повышает реальный лимит Railway и не служит обходом ограничения.

## Доступ и маршрутизация

- Закрытый реестр лежит в `WINDX_DATA_DIR/domains/connections.json`, файлы 0600, каталог 0700. Изменения атомарны; файловая блокировка действует между серверными bundles и процессами. После аварии блокировку нельзя автоматически перехватывать: администратор проверяет `write.lock/owner.json` и отсутствие операции, затем удаляет только эту зависшую блокировку.
- Каждая операция сверяет текущего владельца сайта. Клиент не получает ключ Railway, внутренний provider ID, ownerId или секрет HTTPS-пробы. TXT для DNS намеренно доступен владельцу.
- Неподтверждённая заявка не резервирует домен. Две подтверждённые связи с одним адресом не допускаются. Чужой сайт, смена владельца и неоднозначная связь закрывают доступ.
- Каждый запрос клиентского домена заново сверяет TXT и владельца. Нет сохранённого разрешения после удаления подтверждения. Ошибка DNS даёт 503, отсутствие подтверждения или подключения даёт 404; ответы запрещают кеширование.
- Разрешены только главная опубликованного сайта, `/_enquiry` и служебная HTTPS-проба. Неизвестный Host не открывает кабинет. Входящие внутренние заголовки подключения удаляются и устанавливаются заново после проверки.
- Служебная проба возвращает только случайный challenge и может работать до публикации. Содержимое черновика она не раскрывает.
- HTTPS-проба имеет фиксированные порт 443 и путь, не отправляет cookies, не следует редиректам, проверяет сертификат и ограничивает время и размер ответа. Разрешённый публичный IP закрепляется в соединении после DNS-проверки. Частные и зарезервированные адреса, включая IPv4-mapped IPv6, отклоняются.
- Серверные операции ограничены шестью запусками в минуту на владельца в процессе. Это небольшой предохранитель, не распределённая система ограничения запросов. При дальнейшем масштабировании реестр, блокировка и лимиты потребуют общего хранилища.

## Настройка хостинга

Нужен отдельный Railway project token, ограниченный проектом WINDX и средой production. Создание постоянного доступа согласовывается с владельцем. Секрет хранится в переменной сервиса `WINDX_DOMAIN_RAILWAY_TOKEN`; не добавляется в git, чат, клиентские props или журналы. Используется заголовок `Project-Access-Token`, а не account token.

Railway задаёт `RAILWAY_PROJECT_ID`, `RAILWAY_ENVIRONMENT_ID`, `RAILWAY_SERVICE_ID` и `PORT`. Провайдер перед запросом доменов проверяет scope токена и использует фиксированные service/environment IDs. Приложение не может принять произвольный endpoint API или IDs из браузера. Существующие CLI-аккаунты на компьютере и другие проекты не изменяются.

Адаптер сверяет актуальную GraphQL-схему. Используются значения `CERTIFICATE_STATUS_TYPE_VALID`, `DNS_RECORD_STATUS_PROPAGATED` и `ACTIVE`, а не сокращённые статусы из примеров документации. При потере ответа создания сначала ищется уже созданный домен в том же сервисе, без повторного выделения. Существующий wildcard WINDX не удаляется.

- `npm run build`: production-сборка прошла. Первая попытка внутри песочницы упёрлась в запрет служебного порта Turbopack; после очистки только кеша сборки и разрешённого запуска проверка прошла.

- `node --import tsx tests/domains.mts`: нормализация IDNA/PSL, опасные имена/IP, доказательство владения до provisioning, состояния DNS/TLS/HTTPS, смена владельца, конфликт домена, отключение с ошибкой и повтором, параллельные операции, права файлов, scoped API, лимит и восстановление после потерянного ответа.
- `node --import tsx tests/domains-network.mts`: разбиение TXT на части, ошибка DNS, закрепление IP при обоих режимах lookup, сохранение SNI и проверки сертификата, редирект, неверный challenge, большой ответ, ошибка TLS и смешанный публичный/частный DNS. Сеть полностью подставная.
- `node --import tsx tests/domains-http.mts`: production-сервер с одноразовым хранилищем, опубликованная версия по Host, приём заявки на этом адресе, HTTPS-challenge, изоляция кабинета и чужих посетителей, поддельные заголовки, исчезновение TXT, ошибка DNS, Take offline и повторная публикация, отзыв старой формы, member-only действия и закрытые данные подключения.
- В HTTP-тесте DNS подставлен отдельным явным Node preload только дочернему тестовому процессу. В production-коде нет переменной обхода проверки владения. Настоящий внешний домен не регистрировался, провайдер в тестах заменён.
- Регрессии форм заявок, пробного гостевого сценария и закрытой проверки требований прошли.
- Локальный интерфейс проверен в браузере, включая создание TXT-инструкции и мобильную ширину 390 px без горизонтального переполнения. Тестовый адрес существует только в одноразовой локальной записи, настоящий домен не менялся.

## Команды для повторной проверки

Из каталога проекта:

```sh
npm ci &&
npm run build &&
node --import tsx tests/domains.mts &&
node --import tsx tests/domains-network.mts &&
node --import tsx tests/domains-http.mts &&
node --import tsx tests/enquiries-http.mts &&
node --import tsx tests/guest-trial.mts
```

HTTP-тест поднимает собственный сервер на 3202 и удаляет своё временное хранилище. Существующий dev-сервер останавливать не нужно. При занятости порта тест не следует направлять на чужой процесс.

## Осталось для сквозной проверки

Выбрать отдельный поддомен реально принадлежащего владельцу домена, не затрагивающий работающий сайт. Создать связь в редакторе, вручную добавить выданные TXT и CNAME, дождаться DNS и сертификата, проверить страницу и заявку с телефона, затем Take offline, повторную публикацию и отключение. Проверка настоящего DNS, выдачи сертификата и доставки по внешнему HTTPS не заменяется локальными тестами.

Проверка поиска этапа E пока проверяет адрес WINDX. Отдельный canonical, первичный домен, редирект и аудит поисковой доступности клиентского адреса в эту часть не включены; интерфейс сообщает об этой границе.
