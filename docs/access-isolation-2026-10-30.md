# Личный кабинет и изоляция сайтов

Позднейшее изменение того же дня: по прямому указанию владельца первый результат и первая публикация доступны без регистрации через изолированную гостевую сессию. Текущий сценарий и проверки: [Пробный сайт до регистрации](guest-trial-2026-10-30.md). Описанный ниже запрет общего доступа остаётся, но обязательный вход до первого результата отменён; управление и правки требуют аккаунта.

30 октября 2026. Задача владельца: другие посетители не должны видеть или менять его сайты.

## Причина

После локального прототипа сохранилось одно общее файловое хранилище без аккаунтов и проверки владельца. Это затрагивало не только список: прямые адреса редактора, версий, черновиков и серверные действия тоже не проверяли пользователя. Общий пароль демо, если задан, не разделяет пользователей.

## Исправление

- Вход и регистрация по почте и паролю. Почта здесь служит логином, подтверждение владения почтовым ящиком пока не реализовано.
- Пароль не сохраняется: хранится результат scrypt с индивидуальной солью. Минимум 8 символов при регистрации, изменено по прямой просьбе владельца 1 ноября 2026 года.
- Непрозрачная случайная сессия на семь дней. На сервере хранится хеш токена; cookie HttpOnly, SameSite=Lax, Secure и с префиксом __Host- в production, без общего Domain для клиентских поддоменов. Выход отзывает серверную сессию.
- `getStore()` создаёт хранилище конкретного пользователя после проверки сессии. `OwnedSiteStore` проверяет владельца при каждой операции, включая версии, предложения правок, публикацию, копирование, удаление и код.
- Старые сайты без ownerId недоступны любому новому аккаунту. У них нет автоматического «первого владельца».
- Только публичная опубликованная версия читается через отдельное `getPublicStore()`. Общий перечень опубликованных slug нужен для выбора свободного адреса, но не отдаётся посетителю.
- Лимит попыток входа и регистрации: десять на логин и двести всего за пятнадцать минут в одном процессе. Счётчики сбрасываются при перезапуске. Это временная защита одной реплики, не защита от распределённых атак.

Проверки размещены на границе данных, а не только в меню или перенаправлении страницы. Это соответствует [рекомендации Next.js проверять авторизацию в слое доступа к данным](https://nextjs.org/docs/app/guides/authentication).

## Перенос старых сайтов

Почта владельца зарезервирована до выдачи приглашения. Первоначальный резерв существующего владельца хранится как хеш адреса; дополнительный адрес можно задать WINDX_OWNER_EMAIL. Совпадение почты при обычной регистрации не открывает чужие данные.

Скрипт запускается на сервере с WINDX_DATA_DIR и WINDX_OWNER_EMAIL:

```sh
node scripts/invite-owner.mjs SITE_ID_1 SITE_ID_2
```

Скрипт получает явный список подтверждённых сайтов владельца, создаёт случайный идентификатор аккаунта и код приглашения на 48 часов. Перед добавлением ownerId сохраняет исходные site.json в закрытой папке backups внутри каталога данных. Версии, тексты, факты и статус публикации не меняет. Чужие или неустановленные старые сайты автоматически не присваиваются. Существующий аккаунт и ранее выданное приглашение скрипт не перезаписывает.

Владелец открывает `/login`, выбирает создание аккаунта, вводит свою почту, самостоятельно задаёт пароль и вводит код. Код не попадает в git и не служит постоянным паролем. Повторная регистрация существующего аккаунта запрещена даже с кодом.

## Проверка

```sh
node --import tsx tests/auth-isolation.mts
node --import tsx tests/edit-decoration.mts
node --import tsx tests/ai-json-request.mts
node --import tsx tests/google-auth.mts
npm run build
node --import tsx tests/auth-http.mts
npx tsc --noEmit
git diff --check
```

HTTP-тест запускает локальную production-сборку на 127.0.0.1:3197 с одноразовым каталогом данных. Проверяет разные списки двух аккаунтов, закрытые редактор и предпросмотр, общедоступную только опубликованную версию, прямые POST с чужой сессией и успешное действие владельца. Настоящая модель не вызывается.

В браузере проверены регистрация отдельного локального аккаунта, пустой список без старых сайтов, создание демо-сайта и открытие собственного редактора.

## Ограничения и установка

Установка защиты и исправления JSON-правок проверена на рабочем сервисе: без входа `/sites` ведёт к авторизации и не содержит названий старых сайтов. Пять явно подтверждённых владельцем сайтов перенесены с резервными копиями к идентификатору приглашённого аккаунта. Plainsheet Studio владелец запретил переносить: он не изменён. Пароль задаёт сам владелец при активации приглашения.

Это исправление разделения данных на существующем файловом хранилище, а не завершение всей системы аккаунтов. Нет восстановления пароля, подтверждения почты при парольной регистрации, MFA и распределённого ограничения попыток. Переход на проверенную библиотеку авторизации и базу данных, восстановление и подтверждение почты нужны до широкого клиентского запуска. Новые платные сервисы не подключены.

## Google: код подготовлен, настройка приостановлена

По запросу владельца добавлены регистрация и вход через Google в тот же слой аккаунтов. Используется официальная google-auth-library: authorization code, PKCE, одноразовый state, nonce, проверка подписи ID token, issuer, audience, срока и подтверждения email. Разрешения только openid и email, без доступа к Gmail, Drive, контактам или хранения refresh/access tokens. Кнопка использует [официальный значок и оформление Google](https://developers.google.com/identity/branding-guidelines).

Парольный аккаунт не объединяется с Google только по совпадению почты: это позволило бы захватить заранее зарегистрированный неподтверждённый аккаунт. Для привязки владелец сначала входит с паролем, затем нажимает «Подключить Google» в `/account`. Callback повторно проверяет текущую сессию и совпадение почты. Подключение сохраняет прежний ID аккаунта и сайты. Повторные входы определяются по стабильному Google sub. Для нового Google-аккаунта пароль WINDX не нужен.

Источники: [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect), [проверка токена на сервере](https://developers.google.com/identity/sign-in/web/backend-auth).

Для включения нужны GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET и WINDX_AUTH_ORIGIN=https://www.windx.app. OAuth-клиент типа Web application, callback: `https://www.windx.app/auth/google/callback`. Секрет задаётся только на сервере. Без настройки кнопка Google скрыта, парольный вход продолжает работать. Допустимый домен и адрес возврата берутся из конфигурации, не из произвольного Host.

Владелец разрешил создать отдельный Google Cloud проект без платных сервисов. Открылась форма первоначального принятия Google Cloud Terms; агент не принимал соглашение. Затем владелец явно приостановил настройку Google. Проект, OAuth-клиент и биллинг не создавались. Настоящий вход Google не проверен и не включён. Локальные тесты проверяют state, PKCE, проверку claims, устойчивый ID и безопасную привязку, но не заменяют реальный OAuth-вход после настройки.

Не откатывать рабочий сервис на старую версию с общим открытым кабинетом. Проверить результат установки отдельно: успешная сборка, состояние deployment SUCCESS, вход, чужая ссылка и публичный сайт.

Обнаружена отдельная проблема домена: 30 октября корневой windx.app обслуживается перенаправлением GoDaddy, а www.windx.app ведёт в Railway. POST на корневой домен возвращал 405, вложенный путь 404. До исправления DNS/перенаправления пользоваться www. Это проблема маршрутизации, не доказательство ошибки AI.

## Сопутствующие исправления по сообщениям владельца

- Язык и сортировка: собственная стрелка с фиксированным отступом, без зависимости от системного оформления select.
- `signature.marked-line`: допустимо `mark: "none"`, при котором декоративная линия/обводка/маркер не рисуются, а слова сохраняются. Схема в рабочем промпте синхронизирована. Предпросмотр изменений отмечает смену оформления без выдачи значения mark за текст сайта.
- Промпт правки отделяет язык ответа владельцу от языка сайта. Русская просьба требует русского reply; английский текст сайта сохраняется. Демо-ответы и ошибки русских запросов также переведены. Реальный ответ модели после установки требует отдельной проверки; локальный тест не имитирует платный вызов.
- В журналах сервера найдены невалидные ответы правки: XML-псевдовызов инструмента вместо JSON, пустые ops и потеря обязательного hero при повторе. Эти ответы отклонялись, не меняя сайт. Для правок включён JSON mode на совместимом endpoint, в промпте явно запрещены псевдоинструменты и полный документ вместо patch. Это снижает ошибки формата, но не отменяет проверку схемы и границ правки. Поддержка response_format проверена по публичному списку endpoint текущей модели и [документации OpenRouter](https://openrouter.ai/docs/api_reference/parameters). Платный проверочный запрос не делался.
