# План работы над MVP

Прочитай сначала `docs/master-context.md`, потом `CLAUDE.md`. Этот файл только про порядок работы.

Работаем этапами. В конце каждого этапа остановись, покажи результат, дай точные команды для проверки и жди «дальше». Коммить и пушить после каждого этапа.

Важное ограничение на всё время разработки: **никаких платных сервисов и никаких API-ключей**. Раздел «Пока работаем без платных сервисов» в `CLAUDE.md` обязателен к соблюдению. AI, который нужен для экспериментов и тестовых данных, делаешь ты сам в сессии. В коде обращения к модели идут через слой-посредник с заглушкой. Хранение на старте файлами в проекте.

Что уже есть в репозитории: каркас Next.js 16.4 с TypeScript и Tailwind, черновик модели сайта на zod в `packages/schema`. Это заготовка одного из подходов, а не утверждённая архитектура.

## Этап 1. Закрыть вопрос качества дизайна экспериментом

Главный нерешённый вопрос проекта: как получать сайты с продуманным и разным дизайном. Пока он открыт, остальное строить рано. Этот этап не про красивый код, а про факты, по которым примем решение. Весь AI здесь делаешь ты сам, без вызовов API.

Сравни два подхода на одинаковых входных данных:

- **Подход A, структурированный документ.** Сайт это дерево блоков по схеме (можно опереться на черновик в `packages/schema`). Есть внутренняя библиотека композиций: для одного и того же смысла, например «список услуг» или «почему мы», существует несколько принципиально разных способов подачи, не только карточки. AI выбирает композицию и заполняет содержание, вёрстку пишем мы.
- **Подход B, свободная генерация с ограничениями.** AI сам пишет разметку страницы по жёсткому дизайн-брифу (типографика, сетка, ритм, работа с изображениями, запреты), а качество держится автоматической проверкой результата и повтором при нарушениях.

Возьми три вымышленных лондонских бизнеса с разной природой контента, например мастерская по ремонту велосипедов, частная юридическая практика, студия йоги. Названия и содержание придумай сам, это тестовые данные.

Для каждого подхода и каждого бизнеса сделай:

1. Генерацию сайта из одного текстового запроса, без анкеты.
2. Повторную генерацию того же бизнеса ещё раз, чтобы увидеть разброс.
3. Три последовательные правки запросами: «сделай главный экран спокойнее», «покажи услуги по-другому», «добавь запоминающийся визуальный элемент, подходящий этому бизнесу».

Как это делается без API: промпт ты пишешь в файл, ответ формируешь сам и сохраняешь в файл, дальше код рисует страницу из этого файла. Промпты и ответы остаются в репозитории, потом подставим их в настоящую генерацию без переписывания.

Собери и положи в `docs/experiment-1/`: страницы, которые можно открыть локально, скриншоты всех вариантов, короткий отчёт в `report.md`, использованные промпты в `prompts/` и полученные ответы в `outputs/`.

В отчёте сравни по пунктам:

- Насколько разные композиции получаются у трёх бизнесов и у двух генераций одного бизнеса. Это главный критерий.
- Встречается ли сетка одинаковых карточек с иконками там, где её не просили.
- Что происходит после трёх правок: сайт становится лучше или рассыпается.
- Насколько предсказуем результат: часто ли приходится чинить сломанную вёрстку.
- Сколько примерно токенов уходит на генерацию и на цикл правок, и что это будет стоить, когда подключим настоящую модель. Цифра оценочная, посчитай по длине промптов и ответов.

Закончи отчёт рекомендацией: какой подход берём, либо какая их комбинация, и почему. Решение принимает Максим, твоя задача дать ему факты и честный вывод, включая случай «оба подхода пока не дают нужного качества».

## Этап 2. Ядро создания сайта

Строим на подходе, выбранном по итогам этапа 1.

- Модель данных сайта и хранение версий файлами в проекте. Каждое изменение создаёт новую версию, есть возврат к предыдущей. Доступ к хранилищу через один слой-посредник, чтобы потом переехать на базу без переписывания.
- Простой вход в кабинет и список своих сайтов. Пока без настоящей регистрации и паролей, один локальный пользователь.
- Создание сайта одним текстовым запросом. Уточняющий вопрос задаётся, только если без ответа нельзя сделать сайт, по одному за раз и с объяснением, зачем он нужен.
- Необязательный выбор характера сайта по наглядным примерам, не по названиям стилей. Пропустить его можно в один клик.
- Превью сайта и страница результата.
- Слой `lib/ai` с заглушкой: берёт готовые ответы из `docs/experiment-1/outputs` и из новых заготовок. Интерфейс такой, чтобы настоящий провайдер встал на его место позже.
- Учёт расхода AI на каждое действие, пока оценочный, чтобы дальше считать себестоимость.

## Этап 3. Доработка сайта через AI

- Правки текста, структуры и оформления запросами, с показом изменения до применения.
- Действие «покажи этот раздел иначе», которое даёт действительно другую композицию, а не перекрашенный тот же блок.
- Индивидуальные запоминающиеся элементы под конкретный бизнес.
- История версий и возврат назад.
- Показ оценки стоимости перед дорогим действием, по правилу из `CLAUDE.md`.
- Список неподтверждённых фактов, которые AI придумал (контакты, адрес, часы, цены, цифры, отзывы, обещания), с возможностью подтвердить или удалить.

## Этап 4. Публикация и домен

- Публикация на поддомене сервиса, без обязательного значка конструктора. Пока локально, без настоящего хостинга.
- Подключение собственного домена клиента: продумать сценарий и интерфейс, реальное подключение позже.
- Сводка перед публикацией: что проверено, какие важные задачи открыты, какие сведения не подтверждены.
- Техническая часть, нужная сайту по умолчанию: карта сайта, правила индексации, корректные заголовки, разметка данных, разумная скорость.

## Этап 5. Три проверки рядом с публикацией

Сценарий каждой проверки подробно описан в мастер-контексте, перечитай его перед этапом. Коротко: «Проверить видимость в поиске», «Проверить работу сайта», «Проверить требования к сайту», у каждой свой отчёт обычным языком, задачи по важности, место на сайте, источник факта, предлагаемое исправление и разделение на «исправить автоматически», «нужно решение владельца», «нужен специалист». Часть проверок делается собственным кодом без всякой модели, начни с них.

## Этап 6. Поддержание и рост

Переключатель сопровождения, постоянный контекст конкретного сайта, кнопка «Проверить сейчас», задачи, история «заметили, предложили, согласовали, изменили, измерили», уведомления по почте. Подключение Search Console и аналитики проектируем, но не подключаем.

## Этап 7. Настоящая инфраструктура, последним

Только когда продукт работает на заглушках и решение по дизайну принято:

- Настоящий провайдер модели вместо заглушки: Anthropic напрямую или OpenRouter, выбираем тогда же.
- Переезд хранилища с файлов на базу.
- Настоящий хостинг, поддомены, подключение доменов.
- Регистрация, аккаунты, оплата.

## Порядок работы внутри этапа

Сначала короткий план файлов и структуры, потом код. Длинные файлы разбивай. Перед написанием кода под Next.js 16 читай документацию в `node_modules/next/dist/docs/`.
