# Восстановление WINDX: инструкция оператору

Актуально на 3 ноября 2026 года. Работать из корня checkout. Это не клиентский импорт проекта.

## Получить независимую копию

Нужен GitHub CLI с доступом к приватному `akela1308/windx`:

```sh
npm run backup:pull
```

Команда скачивает artifact последнего успешного запуска `platform-backup.yml` в новый каталог `data/platform-recovery/copies/` и проверяет возраст, ожидаемый ключ и SHA-256. Она не входит в Railway и не просит передавать SSH-ключ в CI.

Если GitHub недоступен, использовать уже скачанный `.windx.enc` на личном устройстве. При доступном Railway зашифрованные файлы находятся в `/data/platform-backups/`; скачивать только по ранее разрешённому SSH-доступу. Не выводить конфигурацию или содержимое аккаунтов в общий журнал.

Проверить, что архив подходит по времени. Обычная проверка скачивания отказывается от снимка старше 30 часов; для аварийной работы с более старым архивом явно оценить потерянный период и использовать CLI восстановления напрямую.

## Восстановить отдельно

Нужен соответствующий закрытый ключ. На исходном Mac он расположен в `data/platform-recovery/private.pem`; не добавлять его в git, GitHub Actions или чат.

```sh
windx_recovery_parent=$(mktemp -d /tmp/windx-recovery.XXXXXX)
npm run backup:restore -- /absolute/path/snapshot.windx.enc data/platform-recovery/private.pem "$windx_recovery_parent/restored"
```

Последний путь должен ещё не существовать. При успехе появятся:

- `restored/data/` — восстановленные аккаунты, сайты, изображения, заявки и остальные канонические данные;
- `restored/configuration.json` — чувствительные настройки, права 600; автоматически не загружаются;
- `restored/restore-summary.json` — дата исходной копии, commit, количества и применённые защитные меры.

Не использовать существующий живой `/data` как цель. При ошибке целостности не пробовать «частично применить» архив.

## Проверить без внешних действий

На чистом checkout нужной версии кода установить зависимости и собрать приложение. Для современных автоматических снимков commit находится в `restore-summary.json`. Исходная ручная копия может содержать `unknown`: для неё использовать явно выбранную совместимую версию, проверенную в отчёте.

```sh
npm ci
npm run build
WINDX_RECOVERY_DRILL="$windx_recovery_parent/restored/data" node --import tsx tests/platform-recovery-http.mts
```

Тест запускает свой localhost-сервер, отключает реальный AI, почту и доменный API, проверяет права, публикации и изображения. Он создаёт временные сессии только в копии, затем удаляет их. Пароли реальных людей не меняются.

Проверки механизма на синтетических данных:

```sh
node --import tsx tests/platform-backups.mts
node --import tsx tests/platform-recovery-http.mts
node --import tsx tests/platform-backup-export.mts
npm run typecheck
npx eslint src ops
```

## Вернуть рабочий сервис

1. Подготовить чистый checkout выбранного commit и отдельный сервис/volume для восстановления либо явно согласованную замену отказавшего сервиса. Не перезаписывать исправную текущую установку.
2. Перенести проверенные данные; восстановить настройки из `configuration.json` в секретные переменные сервера, проверяя актуальность и область действия ключей. Не загружать файл через публичный клиентский интерфейс.
3. Сверить владельцев, текущие и опубликованные версии, изображения и заявки. Старые login/reset/invitation/AI tokens аннулированы намеренно. При необходимости выдать свежие приглашения. Отменённые уведомления о старых заявках разбирать отдельно, без массовой повторной отправки.
4. Проверить зарегистрированные домены, DNS и HTTPS, Google OAuth, доставку служебного письма и новой тестовой заявки. Реестр доменов из архива не создаёт сертификаты и записи у провайдера автоматически.
5. До возврата трафика проверить настройки `ops/platform-backup-config.json` и project/environment/service в workflow: новый сервис имеет другие IDs. Подключить тот же открытый ключ, закрытый серверу не нужен.
6. Развёртывать приложение штатным GitHub Actions → Railway, дождаться SUCCESS. Переключать трафик только после проверки. Сохранять прежний volume и исходный архив до подтверждения результата.
7. Вручную запустить `Encrypted platform backup`, убедиться, что свежий зашифрованный artifact появился вне Railway. Через сутки проверить следующий плановый запуск.

## Контроль и ограничения

- Ежедневная offsite-выгрузка: 04:17 UTC; задержка GitHub scheduler возможна. Это целевой интервал, не SLA и не нулевой RPO.
- В Railway остаются три архива, в GitHub artifacts — 14 дней. Это ограниченное окно, не бессрочное хранение.
- При ошибке workflow сначала проверить свежесть `latest.json`, свободное место, размер, существующий project token, доступность API Railway и логи backup worker. Служебный HTTPS-канал закрыт без проверенного token нужного project/environment; он не отдаёт plaintext или произвольные файлы. Не повышать тариф автоматически.
- Текущие пределы: 100 000 записей, 16 МиБ на файл, 2 ГиБ исходных файлов; для GitHub offsite — 20 МиБ зашифрованного архива. Это операционные ограничения текущего инструмента, не клиентские тарифы. Превышение должно дать ошибку и потребовать пересмотра хранения.
- При появлении нового корневого каталога данных обновить состав резерва и тест восстановления. Копирование неизвестных данных не пропускается молча.
- Хранить закрытый ключ на втором безопасном личном устройстве или в защищённом хранилище. Ключ для старых архивов сохранять до окончания нужного срока хранения.
